# 安全审计：SQL 注入、越权访问和 JWT 漏洞

这个文档直接回答三个问题：代码里有没有 SQL 注入，有没有越权访问，JWT 有没有已知漏洞。结论先说在前面：按当前代码，没有发现这三类高危漏洞，但有几个必须在部署前做对的配置，下面会逐项说明。

## SQL 注入

- 没有拼接 SQL。帖子筛选、分页、频率统计、订阅查询全部用 JPA 和带命名参数的查询，关键词、校区、板块都是参数传进去，不会拼进查询语句里。
- 没有原生 SQL，也没有把用户输入当作表名、列名或排序字段来用。排序固定按创建时间倒序，前端传来的 page 和 size 只用来算分页，不会拼进查询。
- 如果以后要加原生 SQL，必须继续用参数绑定，绝不能用字符串拼接。

## 越权访问

- 所有写操作都以令牌里的公开 ID 为准，不接受请求里传来的 userId。发帖、评论、点赞、收藏、举报、编辑和删除自己的帖子时，后端都会先根据令牌找到当前用户，再核对作者是不是本人。
- 用户 A 不能通过改请求里的 userId 删除用户 B 的帖子，因为删除接口根本不看请求里的 userId，只看令牌和帖子作者是否一致，不一致直接返回无权限。
- 管理员操作只看角色：安全配置里管理接口要求 ADMIN 角色，非管理员调用会直接被拦截，不是只在前端隐藏管理入口。前端隐藏按钮只是体验，真正的安全在后端。
- 匿名帖子的作者信息只在管理端和本人接口里出现，公开接口不返回作者公开 ID 和学号，普通用户无法通过任何公开接口获取其他用户的真实身份。
- 管理员权限也受到限制：管理端用户列表里没有学号，查看学号要单独填理由并记审计日志，审计日志可以在管理后台查看。

## JWT 漏洞

- 算法不是 none，也没有算法混淆问题：用 JJWT 的 HMAC SHA-256 签名，解析时必须用配置的密钥校验签名，签名不对或过期都会被拒绝。
- 令牌里只放公开 ID 和令牌版本号，不放学号，因为令牌内容只是编码不是加密，任何人拿到令牌都能解码。
- 有效期默认 24 小时，解析时会自动校验过期时间，过期令牌会被过滤器拒绝，前端收到 401 后会清除本地令牌并回到登录页。
- 注销问题已经处理：只靠前端清除令牌是不够的，旧令牌在有效期内仍然能用，所以服务端有令牌版本号。注销登录、封禁账号、注销账号时版本号都会递增，旧令牌版本号对不上就会被过滤器直接拒绝。
- 封禁问题已经处理：过滤器和登录接口都会判断封禁状态，临时封禁到期后自动恢复，永久封禁的截止时间为空，不会自动恢复。
- 必须在部署前做对的一件事：把 JWT_SECRET 换成足够长的随机字符串，不要用 .env.example 里的占位值。生产环境用默认密钥等于任何人都能伪造令牌，这个风险不在代码里，在配置里。
- 令牌存在前端本地存储里，这是权衡：优点是前后端分离好实现，缺点是如果页面出现跨站脚本，令牌可能被窃取。缓解办法是前端不使用 v-html 渲染用户内容，Vue 的插值默认会转义用户输入，未来如果要更严格，可以改成 HttpOnly Cookie 方案。

## 仍然要注意的已知限制

- 图片上传已经做了真实文件头校验，只接受 JPEG、PNG、GIF、WebP，拒绝 SVG，但图片本身仍可能包含元数据，未来上线前可以考虑清除图片元数据。
- 频率限制和网络地址哈希只能缓解批量注册和刷帖，不能完全杜绝反复注册规避封禁，需要人工审核配合。
- 令牌版本号方案在多台后端服务器同时运行时需要共享数据库里的版本号，当前实现用数据库字段保存版本号，所以多实例也能一致，前提是数据库是同一个。
